# API and data contracts

All routes except `GET /v1/health` require `Authorization: Bearer <API_TOKEN>`.
No direct client credentials for Ollama, PostgreSQL or GitHub are sent to the browser.
IDs returned by the API are UUIDs. `state` exposes the most recent 200 records of each kind and 50 tasks; older rows remain in PostgreSQL. Add pagination before using very large histories.

| Method / route | Input / result |
|---|---|
| GET /v1/health | Liveness; database is connected during startup |
| GET /v1/state | Profiles, templates, jobs, resumes, evidence, imports, applications, recent tasks |
| POST /v1/assets | Multipart field `file`; returns immutable asset record |
| GET /v1/assets/:id | Authenticated file download |
| POST /v1/resumes/import | `{assetId}` → task; result `{importId, templateId}` |

| POST /v1/templates | `{config, parentId?, unlock?}` → new immutable template; unlock required for a locked parent |

| POST /v1/resumes/tailor | `{profileId, jobId, templateId, prompt, maxPages}` → task; result `{resumeId}` |

## Job-Watcher adapter

`JOB_WATCHER_BASE_URL` includes `/api` (unless you customized the upstream prefix).
The adapter uses the existing contract inspected in the user's repository:

- GET `/jobs?hours=720&limit=25&page=1&search=...`
- Response: `{items:[{id,title,company,location,description,technologies,url,...}], pagination:{page,limit,total,totalPages}}`
- GET `/jobs/:id` returns the complete job row.
- No upstream mutations; no changes to Job-Watcher database or repository.
- Jobs without `description` are rejected instead of inventing a JD from title/tags.
- Optional upstream authorization header comes from `JOB_WATCHER_TOKEN`.

If your live API uses `sourceUrl` instead of `url`, the job can still be analyzed, but add that mapping in `service.ts` to retain the source hyperlink.

## Truth Guard

Validation rejects unknown or unconfirmed fact IDs, duplicate item references and unsupported numeric tokens. All names, historical positions and dates in rendered group/heading are taken from the profile snapshot, not generated by the model. A separate desired-role title is allowed.

Changing or selecting a template makes a new resume revision; old approval never applies to a different revision. User-confirmed profile facts are the source of truth, not an AI verification verdict. The validator does not guarantee semantic entailment: review remains mandatory.

## Task lifecycle and persistence

The queue is stored in PostgreSQL, bounded to 20 pending/running tasks, with one active worker in the API process. Claims use a conditional status update. Run exactly one API instance: startup marks interrupted tasks failed, so multi-instance deployments need a lease/heartbeat design first.

Original files and generated documents are in the `files` Docker volume. PostgreSQL uses the `db` volume. Back up both together. Records are immutable snapshots; there is no delete API in this release. GitHub and URL jobs use network access; resume extraction, AI inference and rendering stay local once dependencies/models are installed.

## Template and document fidelity

Schema is `apps/api/src/schema.ts`. Do not execute user/AI HTML or CSS. Renderer only accepts constrained fields and escapes document content. Playwright requests are blocked during PDF generation, and preview iframe has no script privileges.

Images/icons and raw PDF geometry are retained in import metadata, not laid out as arbitrary components. Export PDF supports single/sidebar templates. DOCX export deliberately uses a readable single-column structure.
